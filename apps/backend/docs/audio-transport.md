# 流式传输评估与音频帧（8.5）

现有实时语音本来就使用二进制 WebSocket 音频；SSE 携带文字、元数据和音频地址，没有把整段音频塞入 Base64。本次选择为实时音频增加可协商的版本、流编号和顺序校验。控制消息与 SSE 保留 JSON，不增加运行时 Protobuf 依赖。

## 协商与兼容

Web/PC 请求 `audio_protocol=framed-v1`，服务端在供应商初始化前返回 `transport_ready`。客户端收到协商后才打开麦克风；旧服务端仅返回 `ready` 时使用原裸二进制。没有参数的旧客户端仍按原协议收发。未知版本拒绝，协商最长等五秒，等待期间挂断可完成退出。

音频包头、字节序、字段和固定对照用例见 [协议定义](../../../packages/audio-transport/README.md)。音频最大 2 MiB，控制事件最大 64 KiB UTF-8。序号从 0 开始、每方向贯穿连接；新语音段编号递增。重复/跳号/畸形包关闭连接，旧段音频丢弃。打断仍由供应商适配器丢弃旧输出，协议头不能修复供应商在上游错误归类的音频。

元数据和音频通过同一个发送锁排序。发送取消先等有界传输完成，再记录序号并传播取消；避免已发送包被复用序号，或未发送包留下跳号。致命连接/协议错误会清理录音轨、VAD 和播放，下一通等待此前清理完成。普通可恢复错误继续保留监听。

实际浏览器还暴露了账号 WebSocket 握手遗漏：客户端提交鉴权子协议时，服务器必须选择一个公开名称。访问中间件现对已授权连接返回 `companion.session`/`companion.device`，从不回显第二项凭据；原有撤销监控保留。

## 编码评估

工具 `tools/benchmark_audio_transport.py` 使用合成字节、3000 次调用的五组中位数。可在隔离环境额外安装 protobuf/pydantic 运行真实 Protobuf 动态消息评估；应用不引入这些额外依赖。当前机器的 4096 字节结果：

| 方式 | 线上字节数 | 编码 µs | 解码 µs |
| --- | --- | --- | --- |
| 原裸二进制 | 4096 | 0.031 | 0.032 |
| 版本化音频帧 | 4116 | 0.510 | 0.591 |
| Protobuf 字节消息 | 4106 | 0.772 | 0.246 |
| 假设的 JSON/Base64 | 5520 | 16.535 | 10.976 |

新帧增加 20 字节，4096 字节音频时约 0.49%。这笔开销用于版本、长度、顺序与流归属。Protobuf 在此样本解码更快、包更小，当前固定帧已满足音频边界，保留简单的两端编解码与可读控制事件。这里没有测网络、模型首响、设备功耗或总体吞吐，不把编码微基准当作端到端提速。

## 验证

Python/TS 固定字节对照、畸形/超限、旧协议往返、新协议双向往返、未知版本、重放、反复取消中发送的序号连续，以及前端握手取消、旧段丢弃、重复序号和致命错误后麦克风清理/再拨通过。

真实隔离 SQL、合成用户与鉴权 WebSocket：默认 O2 `1.2.1.1` 的新版连接收到 111636 字节音频、两轮识别，打断确认后下一轮正常，段号与序号连续；旧裸二进制连接收到 105802 字节音频。输入为真实豆包 TTS 生成的合成语音。

真实 Chrome Web 界面仅使用文件合成麦克风：本地 VAD 触发、25 个上行帧、6 个有效下行帧、6 次实际 AudioBufferSource 播放调度和字幕通过；鉴权握手返回公开协议名。挂断关闭两条录音轨，页面错误为零；保留既有 ScriptProcessor 降级提示。UI 观测包装器只记录原生发送/播放调用，未替代真实实现。
